# گزارش ممیزی امنیتی پروژه

## دامنه و روش بررسی

این ممیزی روی کد مخزن، مسیرها، کنترلرها، middlewareها، سرویس‌های پرداخت/پیامک/موجودی، مدل‌ها، migrationها، قالب‌های Blade، فایل‌های عمومی و تست‌های خودکار انجام شده است. اصلاحات واضح و کم‌ریسک مستقیماً اعمال شده‌اند و تست CI برای آن‌ها اضافه شده است.

**هیچ نرم‌افزاری را نمی‌توان صادقانه «غیرقابل هک» تضمین کرد.** این بررسی جای تست نفوذ مستقل، بررسی تنظیمات واقعی سرور، آزمون شبکه، ارزیابی اپراتور پیامک و تست واقعی درگاه را نمی‌گیرد. نتیجه فعلی یعنی کنترل‌های کدنویسی بررسی و تقویت شده‌اند؛ نه اینکه حمله‌ناپذیری تضمین شده باشد.

## اصلاحات امنیتی انجام‌شده

1. **جلوگیری از Stored XSS در داده ساختاریافته سئو**
   - ورودی‌هایی مثل نام و توضیحات محصول در JSON-LD با JSON_HEX_TAG، JSON_HEX_APOS، JSON_HEX_AMP و JSON_HEX_QUOT کدگذاری می‌شوند.
   - تست تزریق رشته‌ای شامل تگ script اضافه شده است.
2. **Content Security Policy**
   - CSP با nonce تصادفی برای هر پاسخ ساخته می‌شود.
   - اجرای scriptهای inline بدون nonce مجاز نیست.
   - فقط منبع‌های لازم برای فایل‌های محلی، jsDelivr و فونت Google در سیاست مجاز شده‌اند.
   - برای پشتیبانی از استایل‌های inline موجود، unsafe-inline فقط در style-src وجود دارد، نه script-src.
3. **محدودیت تلاش ورود و OTP**
   - ورود مدیر: محدودیت مستقل بر اساس IP و محدودیت جداگانه بر اساس شماره موبایل؛ تغییر IP باعث دور زدن محدودیت شماره نمی‌شود.
   - درخواست OTP: محدودیت مستقل بر اساس IP و محدودیت جداگانه بر اساس شماره موبایل، علاوه بر فاصله زمانی ثبت‌شده برای شماره.
   - تأیید OTP: محدودیت مستقل بر اساس IP و محدودیت جداگانه بر اساس شماره موبایل.
   - پیگیری سفارش و تلاش مجدد پرداخت نیز محدودیت مستقل IP و شماره موبایل دارند.
   - کدهای TOTP مدیر نیز با محدودیت مستقل حساب مدیر و IP محافظت می‌شوند.
4. **جلوگیری از مصرف هم‌زمان OTP**
   - بررسی، افزایش شمارنده تلاش و مصرف نهایی کد در transaction و با قفل ردیف انجام می‌شود.
   - یک کد تأیید پس از مصرف دوباره قابل استفاده نیست.
   - تست‌ها تلاش با IPهای متفاوت برای یک شماره و نیز تلاش با شماره‌های متفاوت از یک IP را بررسی می‌کنند.
5. **محافظت از نشست و داده شخصی**
   - صفحات حساب مشتری، پنل، سبد، checkout و پیگیری سفارش با no-store پاسخ می‌دهند.
   - در محیط production، کوکی session به‌صورت Secure و HttpOnly و SameSite=Lax تنظیم می‌شود.
   - پس از ورود/خروج، شناسه نشست نوسازی می‌شود.
6. **هدرهای مرورگر**
   - X-Content-Type-Options، X-Frame-Options، Referrer-Policy، Permissions-Policy، HSTS در HTTPS و CSP تنظیم شده‌اند.
   - مقدار X-Frame-Options در Apache با middleware هماهنگ شده است.
7. **پرداخت و موجودی**
   - سفارش فقط با verify سمت سرور درگاه پرداخت‌شده می‌شود؛ پارامتر callback به‌تنهایی مدرک پرداخت نیست.
   - مبلغ و Authority در درخواست verify به درگاه ارسال می‌شود.
   - Authority در دیتابیس یکتا است.
   - کسر موجودی، رزرو و جلوگیری از کسر دوباره با transaction و قفل پایگاه داده پیاده‌سازی شده‌اند.
8. **آپلود فایل**
   - تصاویر با اعتبارسنجی نوع فایل و پسوندهای مجاز محدود شده‌اند.
   - مدل سه‌بعدی فقط GLB نسخه ۲ با بررسی ساختار داخلی و بدون وابستگی به فایل خارجی پذیرفته می‌شود.
   - اندازه فایل‌ها محدود است؛ SVG و فایل اجرایی در ورودی‌های تصویر پذیرفته نمی‌شوند.
10. **تأیید دومرحله‌ای مدیر**
   - ورود مدیر پس از رمز عبور به ثبت TOTP در برنامه احراز هویت نیاز دارد؛ بدون آن پنل قابل دسترسی نیست.
   - کلید TOTP با encrypted cast لاراول در دیتابیس رمزنگاری می‌شود.
   - کدهای TOTP با الگوریتم استاندارد HMAC-SHA1 و بازه ۳۰ ثانیه بررسی می‌شوند؛ هر گام زمانی فقط یک‌بار قابل استفاده است.
   - تست بردار استاندارد RFC 6238، فعال‌سازی، ورود و جلوگیری از بازاستفاده کد اضافه شده است.
   - بازیابی دستگاه گم‌شده فقط با فرمان CLI تأییدشده `admin:mfa-reset` انجام می‌شود.
11. **حریم خصوصی پیگیری سفارش**
   - مشاهده سفارش و تلاش مجدد پرداخت فقط برای مشتری واردشده با OTP مجاز است.
   - شماره موبایل سفارش باید با شماره حساب تأییدشده مطابقت داشته باشد؛ مدیر نیز از مسیر مشتری استفاده نمی‌کند.
12. **دسترسی و ورودی‌ها**
   - مسیرهای مدیریتی پشت auth و middleware مدیر هستند.
   - فرم‌های تغییردهنده داده از CSRF محافظت می‌شوند.
   - ورودی‌ها اعتبارسنجی می‌شوند و queryها از binding پارامتری Eloquent/Query Builder استفاده می‌کنند.
   - خروجی عادی Blade به‌صورت escaped نمایش داده می‌شود؛ خروجی‌های JSON-LD که raw هستند، با پرچم‌های امن JSON encode می‌شوند.

## مواردی که هنوز برای انتشار واقعی باید انجام شوند

این‌ها را نباید با تست‌های CI اشتباه گرفت:

- **composer.lock در مخزن وجود ندارد.** تا وقتی lockfile ساخته و commit نشده، نسخه دقیق وابستگی‌ها در نصب‌های بعدی می‌تواند تغییر کند. پیش از انتشار باید lockfile معتبر تولید و همراه پروژه نگهداری شود.
- **تست واقعی زرین‌پال انجام نشده است.** باید با Merchant ID آزمایشی/عملیاتی متعلق به صاحب فروشگاه، درخواست، پرداخت، callback، verify، پرداخت تکراری و لغو واقعی آزمایش شود.
- **تست واقعی پیامک انجام نشده است.** راهنمای عمومی 0098 روش Link-based را با GET و پارامترهای query نشان می‌دهد؛ بنابراین تغییر کورکورانه به POST می‌تواند ارسال را از کار بیندازد. این روش ممکن است اعتبارنامه را در logهای URL ثبت کند؛ برای کاهش ریسک، URL اختصاصی را محرمانه نگه دارید، از HTTPS استفاده کنید و از پنل 0098 درباره endpoint وب‌سرویس SOAP/روش POST اختصاصی سؤال کنید. در صورت دریافت endpoint امن‌تر باید اتصال متناسب با مستندات همان حساب تغییر کند. رمز پیامک را در کد یا Git قرار ندهید.
- **مدیریت بازیابی MFA مدیر باید عملیاتی شود.** اگر مدیر دستگاه احراز هویت را از دست بدهد، بازیابی فقط با فرمان CLI `php artisan admin:mfa-reset 09xxxxxxxxx` روی سرور و پس از تأیید صریح اپراتور انجام می‌شود؛ هیچ مسیر وب یا کد پشتیبان ثابت وجود ندارد. پس از reset، مدیر در ورود بعدی مجبور به ثبت دستگاه جدید است. کلید محرمانه اولیه را در محل امن نگهداری کنید.
- **پیگیری سفارش اکنون به ورود مشتری با OTP نیاز دارد.** دسترسی هر سفارش به تطبیق شماره موبایل حساب تأییدشده و شماره سفارش محدود شده است.
- **محدودیت مصرف کوپن در زمان ساخت سفارش رزرو می‌شود.** سفارش پرداخت‌نشده‌ای که کاربر رها کند ممکن است تا زمان پاک‌سازی/رسیدگی مدیر، ظرفیت یک کد محدود را اشغال کند. پیش از استفاده گسترده از کوپن‌های با ظرفیت محدود، باید انقضا و آزادسازی خودکار رزرو کوپن تکمیل شود.
- **تست CI روی SQLite اجرا می‌شود.** رفتار قفل ردیف و هم‌زمانی باید پیش از راه‌اندازی روی همان نسخه MySQL سرور نیز تست شود.
- **تنظیمات سرور در این ممیزی دیده نشده‌اند.** Document Root باید فقط پوشه public باشد؛ دسترسی وب به .env، vendor، storage، bootstrap/cache، فایل‌های Git و logها باید مسدود باشد.
- **پشتیبان‌گیری، پایش، WAF و محدودیت نرخ در لایه سرور/CDN** باید برای محیط عملیاتی تنظیم شوند. Rate limit برنامه جایگزین محافظت شبکه‌ای در برابر حمله توزیع‌شده نیست.
- **بازپرداخت وجه درگاه به‌صورت خودکار انجام نمی‌شود.** پنل فقط مرجع بازپرداختی را که مدیر پس از انجام آن در درگاه ثبت می‌کند، ذخیره می‌کند.
- **مدل‌های GLB، عکس‌های نهایی، اطلاعات تماس و محتوای واقعی فروشگاه** باید توسط مالک فروشگاه بارگذاری و بررسی شوند.

## چک‌لیست اجباری پیش از انتشار

- [ ] APP_ENV=production
- [ ] APP_DEBUG=false
- [ ] APP_KEY یکتا و قوی، فقط در محیط سرور
- [ ] HTTPS معتبر و تمدید خودکار گواهی
- [ ] SESSION_SECURE_COOKIE=true (در production برنامه نیز آن را enforce می‌کند)
- [ ] Document Root فقط پوشه public
- [ ] عدم دسترسی وب به فایل‌های محیطی، Git، vendor، storage خصوصی و logها
- [ ] رمز مدیر قوی و یکتا؛ ساخت حساب مدیر از مسیر امن و غیرعمومی
- [ ] اطلاعات درگاه و پیامک فقط در environment/secret manager
- [ ] تنظیم مجوز فایل‌ها و پوشه‌ها با حداقل دسترسی لازم
- [ ] فعال بودن backup دیتابیس و فایل‌های آپلودی و آزمایش بازیابی
- [ ] بررسی lockfile و اجرای composer audit
- [ ] تست end-to-end روی MySQL واقعی و درگاه/پیامک sandbox
- [ ] تست بازگشت وجه، callback تکراری، پرداخت هم‌زمان و رزرو موجودی
- [ ] مانیتورینگ خطا، ورودهای ناموفق و پیامک‌های ناموفق

## نتیجه

اصلاحات امنیتی کد و تست‌های مرتبط در مخزن ثبت شده‌اند. انتشار عملیاتی را تا تکمیل موارد بالا، به‌ویژه lockfile، تنظیمات سرور، تست MySQL و تست sandbox درگاه/پیامک، تأیید نکنید.
